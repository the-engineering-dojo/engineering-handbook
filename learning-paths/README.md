# 🛣️ Learning paths

[← Handbook](../README.md) · [🎟️ Practice project](https://github.com/the-engineering-dojo/reservation-engine)

We organize by **engineering questions**, not by a never-ending technology checklist.

## 🌱 Pick your starting point

| Path | Prerequisites | What you should be able to explain |
| --- | --- | --- |
| [🧠 Foundations](01-engineering-foundations.md) | Experience writing services | Why a chosen domain boundary makes sense |
| [🔐 Correctness](02-reliable-data.md) | Basic SQL and APIs | How simultaneous requests affect data integrity |
| [📨 Distributed](03-distributed-systems.md) | Transactions and networking | What to do when delivery fails or repeats |
| [🐳 Cloud-native](04-cloud-native.md) | Basic Linux and HTTP | What changes with two replicas and restarts |
| [🧪 Quality](05-testing-observability.md) | Any running service | How to prove or disprove a claim with evidence |

### 🕒 A sustainable rhythm

**One question per week is enough.** A suggested cycle: 20 minutes reading, 40–90 minutes experimenting, then a short peer discussion. These are suggestions, not deadlines.

### 🏅 What progress means

We do not give points for installing more tools. Progress means you can:
1. explain the problem without jargon;
2. predict and reproduce a failure;
3. compare at least two approaches;
4. show evidence;
5. teach the result to someone else.

Keep each outcome in a [learning note](../templates/learning-note.md).
